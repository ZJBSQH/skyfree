01

ConditionalEdge — 条件路由

是什么

ConditionalEdge 是 LangGraph 中根据当前 State 的值动态决定下一步走向哪个节点的机制。P5 中的 add_edge("A", "B") 是固定路由——A 永远去 B。ConditionalEdge 则允许 A 之后根据条件去 B、C 或 D。

为什么要有

真实写作流程不是线性的。主编审完大纲后，可能"通过→继续"，也可能"驳回→重写"。没有条件路由，你只能把所有节点串成固定管道——这与逐步交互、用户可控的设计目标冲突。

作用

  • 实现审核-驳回-重写循环
  • 根据用户确认结果走不同分支
  • 实现循环节点（如"写一章→确认→写下一章"）
  • 错误处理路由（出错→重试→继续 或 出错→跳过）

使用场景

  • 大纲生成后用户确认：通过 → 人物设计，不通过 → 重写大纲
  • 写稿 Agent 写完一章后：用户满意 → 继续下一章，不满意 → 对话式重写
  • LLM 调用出错时：重试次数 < 3 → 重试，否则 → 降级处理

如何使用

核心 API 是 add_conditional_edges(source, router, mapping)，其中 router 是一个函数，接收 State 返回字符串键；mapping 将键映射到目标节点。

伪代码

# Step 1: 定义路由函数 — 输入 State, 输出字符串键
def review_router(state: NovelState) -> str:
    if state["user_approved"]:
        return "approved"     # 键 → 映射到下一节点
    elif state["retry_count"] < 3:
        return "retry"
    else:
        return "abort"

# Step 2: 构建图 + 添加条件边
builder = StateGraph(NovelState)
builder.add_node("outline", outline_gen)
builder.add_node("character", character_design)

# 关键: 用 conditional_edges 替代 add_edge
builder.add_conditional_edges(
    source="outline",           # 从大纲节点出发
    path=review_router,            # 路由函数 → 返回 "approved"/"retry"/"abort"
    path_map={
        "approved": "character",  # 通过 → 继续
        "retry":    "outline",    # 驳回 → 回路!
        "abort":    END,            # 放弃 → 结束
    }
)

02

interrupt() — 人在回路 (Human-in-the-Loop)

是什么

interrupt() 是 LangGraph 提供的一个特殊函数，在节点内部调用它会暂停整个图的执行，把控制权交还给调用方。调用方拿到当前 State 后，可以通过 Command(resume=...) 注入人工决策并恢复执行。

为什么要有

P5 中的 workflow.invoke(state) 是一口气跑完所有节点的，中间无法停。但 Freesky 的设计要求"每步生成 → 用户确认 → 继续"。如果没有 interrupt，只能把一个大流程拆成多个小 invoke——这破坏了工作流的整体性。

作用

  • 在任意 Agent 执行完后暂停，等待外部输入
  • 保留完整的工作流状态（不需要手动拆流程）
  • 支持用户在暂停点修改 State 后再继续
  • 与 MemorySaver 配合可实现跨会话的暂停-恢复

使用场景

  • 大纲生成后暂停 → 用户审核 → 通过则继续，驳回则修改 state 后重试
  • 每章写完后暂停 → 用户阅读 → 满意继续 / 不满写批注 → Agent 按批注重写
  • 敏感操作前暂停（如删除项目）等待二次确认

如何使用

三步配合：① 节点内调用 interrupt("提示信息") 暂停；② 外部用 workflow.invoke(state, config) 触发直到暂停点；③ 用 Command(resume=用户输入) 恢复执行。

伪代码

# ═══ 图定义侧: 在节点中调用 interrupt() ═══
from langgraph.types import interrupt

def outline_node(state: NovelState) -> dict:
    # 1. 执行业务逻辑 — 生成大纲
    outline = model.invoke(state["inspiration"])

    # 2. 暂停! 把大纲交给用户审核, 等待他回复
    user_feedback = interrupt({
        "message": "大纲已生成, 请审核",
        "outline": outline,
        "action": "approve/revise/abort",
    })

    # 3. 恢复后, user_feedback  = Command(resume=...) 传入的值
    if user_feedback == "approve":
        return {"outline": outline, "messages": [outline]}
    elif user_feedback == "revise":
        return {"retry_count": state["retry_count"] + 1}
    else:
        return {"aborted": True}


# ═══ 调用侧: 触发执行 → 拿到中断信息 → 用户决定 → 恢复 ═══
from langgraph.types import Command

config = {"configurable": {"thread_id": "session-1"}}

# 第一步: 执行到 interrupt() 处暂停
result = workflow.invoke(initial_state, config)
# result  = 被中断时的 state 快照 (包含 interrupt 传入的消息)
# workflow 此刻处于 "interrupted" 状态

# 外部世界 — 用户看大纲, 做决定
user_decision = input("大纲满意吗? (approve/revise/abort): ")

# 第二步: 把用户决定注入, 从断点继续执行
final_result = workflow.invoke(
    Command(resume=user_decision),  # ← 这个值变成 user_feedback
    config,                          # ← 同一个 thread_id!
)
关键理解：interrupt() 不是"终止"，而是"挂起"。图的内部状态被保存（尤其是配合 MemorySaver 时），恢复后从中断的下一行代码接着执行，而不是重新跑整个节点。
03

MemorySaver — 状态持久化

是什么

MemorySaver 是 LangGraph 提供的一个 Checkpointer（检查点存储器）。它在每次图执行到一个"步骤"（super-step）时自动保存完整的 State 快照。使用 thread_id 区分不同的对话/会话。

为什么要有

没有 MemorySaver 时，每次 workflow.invoke() 都是独立的一次执行——上次跑完的 State 全丢了。P5 的做法是把所有结果拼进一个巨大的 initial_state 再 invoke，这既低效又无法支持真正的"多轮对话"。

作用

  • 跨轮调用：第二次 invoke 能自动拿到上次的完整 State
  • 中断恢复：与 interrupt() 配合，中断后可以从任意时间点恢复
  • 回溯能力：可查看历史 checkpoint，甚至"回退"到之前的状态
  • 多会话隔离：通过 thread_id 隔离不同用户/项目的上下文

使用场景

  • 写作助手的多轮交互：用户在对话中反复修改大纲、人物等
  • 长时间创作任务：写到第 10 章时关闭浏览器，下次打开能从断点继续
  • A/B 分支：从某个 checkpoint fork 出两条不同的创作方向

如何使用

只需要两步：① 创建 MemorySaver 实例；② 在 builder.compile(checkpointer=memory) 时传入。之后每次 invoke 都带上 config={"configurable": {"thread_id": "xxx"}}。

伪代码

from langgraph.checkpoint.memory import MemorySaver

# 1. 创建 MemorySaver
memory = MemorySaver()

# 2. 编译时注入
workflow = builder.compile(checkpointer=memory)

# ═══ 第一次调用: 用户输入灵感 ═══
config = {"configurable": {"thread_id": "project-42"}}
result1 = workflow.invoke(
    {"inspiration": "穿越修真界", "outline": "", ...},
    config  # ← 必须传 thread_id
)
# 此时 MemorySaver 已自动保存了 result1 的完整 State

# ═══ 第二次调用: 用户补充需求, 自动继承上次状态! ═══
result2 = workflow.invoke(
    {"user_feedback": "主角加一个妹妹角色"},
    config  # ← 同一个 thread_id, MemorySaver 自动加载上次 state!
)
# result2 中: outline / characters 等字段都还在
# 只有 user_feedback 被更新为新值

# ═══ 查看历史状态 ═══
checkpoints = list(memory.list(config))
# 返回所有 checkpoint 的时间线, 每个包含当时的完整 state
注意：MemorySaver 存在内存中——进程重启后全部丢失。生产环境需要换用 SqliteSaver 或 PostgresSaver。但它对学习和本地开发完全够用。
04

Supervisor vs Peer — 协作范式对比

这是多 Agent 系统中最核心的架构选择。P5 的固定流水线只是入门——当你需要 Agent 之间能互相调用、根据情况灵活切换时，就得在 Supervisor 和 Peer 之间做取舍。

范式一 Supervisor（主管模式）

是什么

一个中心化的 Supervisor Agent 负责分析任务状态，决定下一步调用哪个 Worker Agent。Worker 之间不直接通信，所有协调都经过 Supervisor。

为什么要有

当任务可以分解为"先做A还是先做B"的决策时（且决策逻辑比较复杂），中心化控制最直观。Supervisor 天然知道全局状态，天然适合 ConditionalEdge 做动态路由。

作用 / 使用场景

  • 写作流程编排：主编决定"先大纲再人物"还是"因灵感充分直接跳写稿"
  • 代码审查：Supervisor 决定先查安全漏洞还是先查性能问题
  • 客服路由：Supervisor 根据用户意图分配到退换货/技术支持/投诉

优势 vs 劣势

  • ✓ 决策逻辑集中，易理解、易调试
  • ✓ 天然防循环（Supervisor 统一控流）
  • ✗ Supervisor 是单点瓶颈
  • ✗ 复杂任务下 Supervisor 的 prompt 可能很长

有向图

范式二 Peer（对等协作模式）

是什么

没有中心控制者。每个 Agent 地位平等，各自决定"我做完后该把消息发给谁"。Agent 之间通过共享的消息通道（Messages）直接通信。

为什么要有

当任务高度不确定，Agent 之间的调用关系无法预定义时，对等协作更灵活。比如"角色 Agent 发现需要补充世界观设定"，在 Supervisor 模式下必须经过主管中转，而 Peer 模式下可以直接 → worldbuilding。

作用 / 使用场景

  • 开放讨论：两个 Agent 互相辩论直到达成共识
  • 互相补全：写稿时发现需要新角色 → 直接找人物 Agent
  • 多轮修正：润稿 Agent 发现问题 → 直接找写稿 Agent 重写

优势 vs 劣势

  • ✓ 更灵活，Agent 直接沟通，不需要主管中转
  • ✓ 无单点瓶颈，每个 Agent 独立决策
  • ✗ 可能无限循环（A→B→A→B...）
  • ✗ 调试困难，问题出在哪很难追踪

有向图

对比总览

维度Supervisor（主管）Peer（对等）
控制流中心化：Supervisor 统一调度去中心化：Agent 自行路由
拓扑结构星型：Supervisor ↔ Workers网状：Agent ↔ Agent
路由方式Supervisor 节点的 ConditionalEdge每个 Agent 节点的 ConditionalEdge
循环控制天然可控（Supervisor 把关）需显式终止条件（如最大轮数）
适用场景流程可预定义，决策逻辑集中流程不确定，需 Agent 自主协商
调试难度低（所有决策在 Supervisor）高（问题可能在任何一条边上）
实现方式单图 + Supervisor 节点 + ConditionalEdge单图多条 ConditionalEdge，或子图嵌套
兼容性说明：Supervisor 和 Peer 是互斥的架构选择——你不能在同一个图中既让 Supervisor 做中心调度，又让 Worker 自行路由到其他 Worker。它们是两种不同的图拓扑。你可以根据业务场景切换：Freesky 的"从零创作"用 Supervisor，"对话式修改"用 Peer。
05

综合实战 — 可运行代码

在一份代码中联合使用 Supervisor + ConditionalEdge + interrupt() + MemorySaver

这四个特性天然兼容：Supervisor 用 ConditionalEdge 做动态路由；interrupt() 挂在各 Worker 后面等用户确认；MemorySaver 保存所有中间状态。它们共同构成一个"中心调度 + 动态路由 + 人在回路 + 状态持久"的完整系统。

完整代码

#!/usr/bin/env python3
"""
P6 — LangGraph 进阶综合演示
Supervisor + ConditionalEdge + interrupt() + MemorySaver

运行方式:
  pip install langgraph langchain-openai python-dotenv
  python p6_supervisor_demo.py
"""

import os
from typing import TypedDict, Annotated, Literal
from dotenv import load_dotenv

from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import interrupt, Command

load_dotenv()


# ═══════════════════════════════════════
# 1. 状态定义
# ═══════════════════════════════════════
class NovelState(TypedDict):
    inspiration: str
    outline: str
    characters: str
    messages: Annotated[list, add_messages]
    next_worker: str              # Supervisor 决定下一步
    user_decision: str            # 用户反馈


# ═══════════════════════════════════════
# 2. LLM 初始化
# ═══════════════════════════════════════
model = init_chat_model(
    model=os.getenv("LLM_MODEL", "qwen2.5:3b"),
    model_provider="openai",
    base_url=os.getenv("LLM_BASE_URL", "http://localhost:11434/v1"),
    api_key=os.getenv("LLM_API_KEY", "ollama"),
    temperature=0.7,
)


# ═══════════════════════════════════════
# 3. Worker Agents
# ═══════════════════════════════════════

def outline_worker(state: NovelState) -> dict:
    """大纲Worker: 生成大纲 → interrupt等用户确认"""
    inspiration = state["inspiration"]
    prompt = f"请为以下灵感设计10章故事大纲:\n{inspiration}"
    response = model.invoke(prompt)
    outline = response.content

    # ★ interrupt: 暂停, 把大纲交给用户审核
    user_feedback = interrupt({
        "stage": "outline_review",
        "outline": outline,
        "prompt": "大纲满意吗？(ok=继续 / redo=重写 / edit:xxx=按批注重写)",
    })

    # 根据用户反馈决定行为
    if user_feedback.startswith("edit:"):
        # 用户给了批注 → 重新生成
        edit_note = user_feedback[5:]
        prompt2 = f"请修改大纲, 批注:\n{edit_note}\n\n原大纲:\n{outline}"
        response2 = model.invoke(prompt2)
        outline = response2.content
    elif user_feedback == "redo":
        response = model.invoke(prompt + "\n请用完全不同的结构重新设计。")
        outline = response.content

    return {"outline": outline, "messages": [outline]}


def character_worker(state: NovelState) -> dict:
    """人物Worker: 生成人物档案 → interrupt等用户确认"""
    prompt = f"灵感:{state['inspiration']}\n大纲:{state.get('outline','')}\n请设计主角+1个反派+2个配角。"
    response = model.invoke(prompt)
    characters = response.content

    user_feedback = interrupt({
        "stage": "character_review",
        "characters": characters,
        "prompt": "人物满意吗？(ok/redo/edit:xxx)",
    })

    if user_feedback.startswith("edit:"):
        edit_note = user_feedback[5:]
        prompt2 = f"修改人物, 批注:{edit_note}\n原档案:{characters}"
        response = model.invoke(prompt2)
        characters = response.content
    elif user_feedback == "redo":
        response = model.invoke("请全部重新设计人物档案:\n" + prompt)
        characters = response.content

    return {"characters": characters, "messages": [characters]}


# ═══════════════════════════════════════
# 4. Supervisor — 核心：用 ConditionalEdge 做动态路由
# ═══════════════════════════════════════

# Supervisor 的 LLM 决策: 分析 state 后输出 "outline"/"character"/"FINISH"
SUPERVISOR_PROMPT = """你是写作主编。根据当前状态决定下一步。

规则:
- 如果大纲为空, 先调用 outline
- 如果大纲有内容但人物为空, 调用 character
- 如果大纲和人物都有内容, 回复 FINISH

当前状态:
  大纲: {outline_status}
  人物: {character_status}

只输出: outline / character / FINISH"""

def supervisor_node(state: NovelState) -> dict:
    """Supervisor — 分析状态, 决定下一步"""
    prompt = SUPERVISOR_PROMPT.format(
        outline_status="已有" if state.get("outline") else "空",
        character_status="已有" if state.get("characters") else "空",
    )
    response = model.invoke(prompt)
    decision = response.content.strip()
    print(f"\n[Supervisor] 决策: {decision}")
    return {"next_worker": decision}


# ★ 路由函数 — ConditionalEdge 的核心
def supervisor_router(state: NovelState) -> str:
    decision = state.get("next_worker", "")
    if decision == "outline":
        return "outline"
    elif decision == "character":
        return "character"
    else:
        return "finish"


# ═══════════════════════════════════════
# 5. 构建图
# ═══════════════════════════════════════

builder = StateGraph(NovelState)

builder.add_node("supervisor", supervisor_node)
builder.add_node("outline", outline_worker)
builder.add_node("character", character_worker)

builder.add_edge(START, "supervisor")

# ★ ConditionalEdge: Supervisor 根据决策分叉
builder.add_conditional_edges(
    source="supervisor",
    path=supervisor_router,
    path_map={
        "outline": "outline",
        "character": "character",
        "finish": END,
    },
)

# Worker 完成后, 回到 Supervisor 继续决策
builder.add_edge("outline", "supervisor")
builder.add_edge("character", "supervisor")

# ★ MemorySaver: 状态持久化
memory = MemorySaver()
workflow = builder.compile(checkpointer=memory)


# ═══════════════════════════════════════
# 6. 交互式运行
# ═══════════════════════════════════════

def run_interactive():
    """交互式演示 — 每次中断都等待用户输入"""

    thread_id = "demo-session-1"
    config = {"configurable": {"thread_id": thread_id}}

    inspiration = input("请输入故事灵感: ").strip()
    if not inspiration:
        inspiration = "主角穿越到修真世界，获得了仇恨值面板"

    initial_state: NovelState = {
        "inspiration": inspiration,
        "outline": "",
        "characters": "",
        "messages": [],
        "next_worker": "",
        "user_decision": "",
    }

    # 主循环: 反复 invoke, 直到没有中断
    state = initial_state
    while True:
        try:
            # invoke 会执行到下一个 interrupt() 或 END
            result = workflow.invoke(state, config)

            # 如果顺利结束
            print("\n✅ 创作完成!")
            print(f"大纲: {result.get('outline', '')[:300]}...")
            print(f"人物: {result.get('characters', '')[:300]}...")
            break

        except Exception as e:
            # interrupt() 抛出特殊异常 — 显示中断信息
            print(f"\n⏸ 工作流暂停, 等待你的决定...")
            print(f"提示: {e}")

            user_input = input(">>> 你的决定 (ok/redo/edit:xxx/abort): ").strip()
            if not user_input:
                user_input = "ok"

            if user_input == "abort":
                print("❌ 用户终止")
                break

            # ★ 用 Command(resume=...) 恢复执行
            state = Command(resume=user_input)


if __name__ == "__main__":
    run_interactive()

Peer 模式独立演示

为何与 Supervisor 分离：Peer 模式中每个 Agent 自行决定下一个被调用者——这需要每个节点都有自己的 ConditionalEdge（或图中有特殊的路由汇聚点），与 Supervisor 的单一路由点完全不兼容。它们是两种不同的图结构，不能同时存在于同一个 StateGraph 中。

Peer 模式代码

"""
P6 — Peer 对等协作模式独立演示
每个 Agent 完成后自行决定"下一个是谁"
"""

from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages


class PeerNovelState(TypedDict):
    inspiration: str
    outline: str
    characters: str
    worldbuilding: str
    messages: Annotated[list, add_messages]
    next_speaker: str          # 每个 Agent 自行设置
    round_count: int           # 防无限循环
    max_rounds: int


# ═══ 每个 Peer Agent: 做自己的事 → 决定下一个谁 ═══

def outline_peer(state: PeerNovelState) -> dict:
    """大纲Peer: 生成大纲, 然后决定: 找人物帮忙 or 直接结束"""
    if state.get("outline"):
        # 已有大纲, 不需要重复做
        return {"next_speaker": "character"}

    outline = "【生成大纲逻辑】"

    # 决定下一个被调用者
    if state["round_count"] < state["max_rounds"]:
        next_one = "character"   # 下一步: 人物设计
    else:
        next_one = "FINISH"

    return {
        "outline": outline,
        "messages": [outline],
        "next_speaker": next_one,
        "round_count": state["round_count"] + 1,
    }


def character_peer(state: PeerNovelState) -> dict:
    """人物Peer: 设计角色, 如果缺少世界观 → 找世界观Peer"""
    if state.get("characters"):
        return {"next_speaker": "worldbuilding"}

    characters = "【生成人物逻辑】"

    # ★ 自主决策: 看出界观设定了吗? 没有就找人帮忙
    if not state.get("worldbuilding"):
        next_one = "worldbuilding"  # 直接找世界观 Peer!
    elif state["round_count"] < state["max_rounds"]:
        next_one = "worldbuilding"  # 还可以再讨论一轮
    else:
        next_one = "FINISH"

    return {
        "characters": characters,
        "messages": [characters],
        "next_speaker": next_one,
        "round_count": state["round_count"] + 1,
    }


def worldbuilding_peer(state: PeerNovelState) -> dict:
    """世界观Peer: 构建世界观, 可能回找人物Peer补充"""
    if state.get("worldbuilding"):
        return {"next_speaker": "FINISH"}

    worldbuilding = "【生成世界观逻辑】"

    # ★ 世界观可能触发新的人物需求 → 回找人物Peer
    if "新势力" in worldbuilding and state["round_count"] < state["max_rounds"]:
        next_one = "character"   # ← 回路! 回找人物补充
    else:
        next_one = "FINISH"

    return {
        "worldbuilding": worldbuilding,
        "messages": [worldbuilding],
        "next_speaker": next_one,
        "round_count": state["round_count"] + 1,
    }


# ═══ 路由函数 — 读 next_speaker, 决定去哪个节点 ═══

def peer_router(state: PeerNovelState) -> str:
    next_speaker = state.get("next_speaker", "FINISH")
    # 防止无限循环: 到了最大轮数强制结束
    if state["round_count"] >= state["max_rounds"]:
        return "finish"
    if next_speaker in ("outline", "character", "worldbuilding"):
        return next_speaker
    return "finish"


# ═══ 构建图 ═══

builder = StateGraph(PeerNovelState)

builder.add_node("outline", outline_peer)
builder.add_node("character", character_peer)
builder.add_node("worldbuilding", worldbuilding_peer)

builder.add_edge(START, "outline")   # 入口固定: 从大纲开始

# ★ 每个节点都接 ConditionalEdge — 各自决定下一个目标
builder.add_conditional_edges("outline", peer_router, {
    "character": "character",
    "worldbuilding": "worldbuilding",
    "finish": END,
})
builder.add_conditional_edges("character", peer_router, {
    "outline": "outline",
    "worldbuilding": "worldbuilding",
    "finish": END,
})
builder.add_conditional_edges("worldbuilding", peer_router, {
    "character": "character",
    "finish": END,
})

workflow = builder.compile()

result = workflow.invoke({
    "inspiration": "穿越修真界",
    "outline": "",
    "characters": "",
    "worldbuilding": "",
    "messages": [],
    "next_speaker": "outline",
    "round_count": 0,
    "max_rounds": 6,  # 安全阀: 最多6轮
})
Peer 模式的关键设计：
  • 入口固定：从大纲开始（add_edge(START, "outline")），之后完全自主
  • 路由共享：三个节点公用同一个 peer_router 函数，但每个节点的 path_map 不同——outline 不能路由到自己，character 可以回路到 outline
  • 安全阀：round_count + max_rounds 防止无限循环（Peer 模式最容易出的问题！）
  • 可与 interrupt + MemorySaver 结合：在每个 Peer 节点内加 interrupt() 就变成了"对等协作 + 人在回路"
